# Test plan — #164, offline deploy (`gui_app.py` 0.30.0)

*Nothing headless can drive wx, so all of this is by hand.*

## What actually changed, so you know where to look

- `DeployPanel` gained an offline mode — **Export** instead of Write.
- `ProfileListPanel.on_export()` was **extracted** to a shared
  `export_working_copy()`. Both panels call it. **So the connected path
  and the existing offline Export both run changed code**, even though
  neither was supposed to change behaviour.
- `PreflightPanel`'s deploy-time `assert_mode` was **deleted**.

That middle point is why **section A matters as much as B**. The bug was
offline, but the refactor touched the path you use every day.

## B. Offline edit flow — ⚠ REWRITTEN 2026-10-25, the original was wrong

**What section B first said:** offline, edit a screen → Pre-Flight →
Deploy, and check the Deploy page shows Export.

**That path does not exist**, and Doug walked into the discrepancy
rather than the bug. Offline, `ViewScreensPanel`'s button becomes
**"Export Profile..."** and dispatches **straight to the save dialog** —
by design since #141. `show_panel("review")` has exactly one caller and
it is the device-mode branch, so **Pre-Flight and Deploy are unreachable
offline by this route.**

So #164 never affected the ordinary offline edit flow. It affects the
two flows that navigate DIRECTLY to `DeployPanel` — **clone** and
restore — which is section C.

**What Doug saw is a PASS, and a useful one.** That flow now runs the
extracted `export_working_copy()`, so walking it exercises the
refactor:

| # | check | expect | 2026-10-25 |
|---|---|---|---|
| B1 | the button on the screens view | "Export Profile..." | **pass** |
| B2 | pressing it | save dialog straight away, no intervening page | **pass** |
| B3 | after saving | "Verified twice" message naming the CRC | **pass** |
| B4 | where you land | back on the screens view, button still live | **pass** |
| B5 | no Deploy page appears at all | correct — it is not on this path | **pass** |

B4 is right rather than a leftover: you may want to export again, to a
second location or under another name.

## D. The filename guard still guards

Offline, Export, and deliberately **rename the file** in the save dialog.

Expect the warning that the Edge matches by filename and will accept-
then-ignore anything else, offering to save under the right name
instead. That warning is one of the three behaviours the extraction had
to preserve, so it is worth provoking once.

**PASS, 2026-10-26.** The warning fired on rename, so the guard
survived being lifted out of `ProfileListPanel` into
`export_working_copy()`. Together with B3's "verified twice" message
that accounts for all three of the behaviours the extraction could
have dropped: the filename warning, the CRC check before writing, and
the read-back compare.

> **Footnote worth keeping, from the same day.** Doc revs 183 and 184
> established that this warning's *claim* is false — the Edge accepts
> and imports a differently-named file, for a new profile and for a
> replacement. What the filename appears to control is whether the
> device rewrites the file rather than whether it reads it. So the
> warning is correct to exist and wrong in what it says, and rewording
> it is a separate job from this test. What D confirms is only that
> the extraction preserved it.

## E. Mode switching in one session — the thing most likely to be broken

⚠ **Step 2 corrected 2026-10-26**, from Doug asking how to reach the
Deploy page offline. The original said "reach the Deploy page again"
without saying how — and per section B, the offline *edit* flow never
goes there. **Offline you must CLONE**, which is one of only two routes
(clone and restore) that navigate directly to `DeployPanel`. Third
section of this plan to be under-specified in the same way.

The panel instance is **reused** across mode switches and the labels
are set in `_refresh()`. If that is wrong, a label from one mode
survives into the other.

| step | do | expect | 2026-10-26 |
|---|---|---|---|
| E1 | **Connected**: edit a screen → Review & Deploy → the Deploy page. Do **not** write — reaching it is the test | "Deploy to Device", "Write to Device (NewFiles) →", eject/check **visible** | **pass** |
| E2 | Back out, switch to **offline**. The 530 can stay plugged in and un-ejected | — | **pass** |
| E3 | **Offline: clone a profile** → it lands on the Deploy page. Cancel rather than exporting | "Export Profile", "Export...", eject/check **gone, not greyed** | **pass** |
| E4 | Back, re-detect, **connected** again | — | **pass** |
| E5 | Reach the Deploy page a third time | everything from E1 is **back** | **pass** |

**E PASSES, 2026-10-26.** E3 observed in full: "Export Profile"
heading, "Export..." button, **Done greyed but visible** (it enables
only after a successful export), "‹ Back to Clone Setup" live, and no
eject or check buttons anywhere. E5 returned every connected-mode
label correctly.

**E5 is the real test.** E1–E3 would pass even if the labels were set
once and never refreshed; only the return trip catches a stale one.

**Leaving the device plugged in during E2 is safe by design**, not by
luck: `enter_offline_mode()` sets `garmin_root = None` deliberately, so
no device-only path has anything to reach for even if a mode check were
missed.
