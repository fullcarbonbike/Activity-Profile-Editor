## B. The ordinary case must not regress — ✅ PASSED 2026-10-28

> ⚠ **B2 as originally written was wrong, and contradicted B1.** It
> said Check should report "that change and nothing else". **It should
> report NO differences.** `on_check()` calls
> `describe_screen_changes(editing_path, live_path)` — what was *sent*
> against what is *live*. A successful deploy makes those identical, so
> "no difference" IS the pass, and Check naming your edit would mean
> the write had not landed. Pre-Flight is the panel that lists the
> change against the original; Check verifies arrival. I asserted the
> wrong expectation to Doug mid-test before reading `on_check()`.

| # | do | expect | result |
|---|---|---|---|
| B1 | edit a screen on an existing profile, deploy under its own name, Check | verifies cleanly, as it always did | **pass** |
| B2 | Check after that deploy | **no differences** — sent matches live | **pass** — `ROAD_T1`, 2026-10-28 |
| B3 | **Pre-Flight**, before deploying | lists the real change | **pass** — showed "Power Graph → Battery Level" |

**Pre-Flight is where the "does it still find things?" risk gets
tested**, since Check structurally cannot. The two panels in sequence
on the `ROAD_T1` run — Pre-Flight naming the change, Check reporting

Corroborated headlessly. Diffing the baseline against the

### (superseded) C — ⚠ rewritten 2026-10-27, its premise was wrong

### What C used to say, and why it was wrong

> *"Per Doc rev 184 an import under a non-canonical filename is the way
> to provoke it. C1: export under a deliberately odd name
> (`test99.fit`)."*

**A2 already ran that experiment and it did not provoke anything.**
`zztest.fit` is as non-canonical as a name gets, and the returned file
has every screen in its original slot. So C as written would have
passed without testing the pairing — the exact trap C3 was added to
catch, reproduced inside the step meant to prevent it. Rev 184 listed
the filename as *one confounded candidate*, not as the trigger; I
promoted it to a recipe it was never evidence for.

### What we actually know about provoking it

| case | renumbered? |
|---|---|
| `ROAD_22`, **840**, **new** profile, non-canonical name | **yes** |
| `ROAD A2`, **530**, **new** profile, non-canonical name | **no** |

The filename is now ruled out as a sufficient cause. What still
differs is the **model** — and the 840 cannot enter device mode, so
the one configuration known to renumber cannot be driven by the GUI at
all.

### So C becomes an attempt, not a step with a predicted result

| # | do | expect |
|---|---|---|
| C1 | take a profile **already on the 530**, change one field, deploy it under its own name, restart, **Check** | reports **only the field you changed** |
| C2 | pull the file afterwards and send it to me | I say whether the slots moved |

**Neither outcome is a failure of this release.** If C2 shows no
movement, we have simply not found a way to make a 530 renumber, and
#162 ships on its headless proof — 0 differences where the old pairing
reported 11, on the real `ROAD_22` pair. If C2 shows movement, C1's
clean report is the hardware confirmation.

What C must **not** do is report a pass on C1 alone. Without the file,
C1 says nothing.
